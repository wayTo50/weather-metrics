# Weather Metrics

Weather Metrics is a small Spring Boot service that stores readings from weather sensors.

Each reading contains a sensor ID, temperature, humidity, wind speed, and the time it was recorded. The API can return
the average temperature for all sensors or for one sensor over a given time range.

## Run the application

You need Java 17, Maven, and Docker.

```bash
docker compose up -d
mvn -pl server -am install
mvn -pl server spring-boot:run
```

The application starts on `http://localhost:8080`.

If you ran an older version of the project, reset the local database first:

```bash
docker compose down -v
docker compose up -d
```

The database connection can be changed with `DATABASE_URL`, `DATABASE_USERNAME`, and `DATABASE_PASSWORD`.

## Run the tests

```bash
mvn test
```

The tests use H2, so PostgreSQL does not need to be running. The project has unit tests, controller tests, repository
tests, and integration tests that call the APIs through the client module.

## API examples

Here are a few curl examples for checking the API by hand.

### curl

Register a sensor reading:

```bash
curl -X POST "http://localhost:8080/api/v1/readings" -H "Content-Type: application/json" -d '{"sensorId":"sensor-1","temperatureCelsius":18.75,"humidityPercent":63.5,"windSpeedMps":4.2,"recordedAt":"2026-08-26T10:30:00Z"}'
```

Get the average temperature across all sensors:

```bash
curl "http://localhost:8080/api/v1/metrics/temperature/average?from=2026-08-26T00:00:00Z&to=2026-08-27T00:00:00Z"
```

To query one sensor, add its ID:

```bash
curl "http://localhost:8080/api/v1/metrics/temperature/average?from=2026-08-26T00:00:00Z&to=2026-08-27T00:00:00Z&sensorId=sensor-1"
```

List the sensor IDs that have sent readings:

```bash
curl "http://localhost:8080/api/v1/sensors"
```

The time range includes `from` but does not include `to`. If no readings match, the response contains a null average.

Humidity and wind speed are stored, but only temperature averages are exposed by the query API.

### Postman

Import `postman/Weather Metrics.postman_collection.json` into Postman, start the application, and run the collection.
It registers sample readings and checks all API endpoints. The collection uses `http://localhost:8080` by default;
change its `baseUrl` variable if the application runs on another address.

### Clean up test data

This removes all readings but keeps the database schema and Flyway history:

```bash
docker compose exec postgres psql -U weather_metrics -d weather_metrics -c "TRUNCATE TABLE sensor_readings;"
```

Run the command from the project directory while PostgreSQL is running.

## Project modules

- `common` contains the request and response DTOs.
- `client` contains a Java client for calling the API.
- `database-migration` contains the Flyway migration.
- `server` contains the controller, service, repository, entity, mapper, and exception handling.
- `integration-test` starts the server and tests the APIs through the client.

## Notes

- PostgreSQL stores the readings and calculates averages with `AVG`.
- Flyway creates the database schema.
- `received_at` is generated by PostgreSQL when a reading is inserted.
- The indexes support queries by time range and by sensor ID plus time range.
- Duplicate-reading handling is not included in this version. In a production service, I would agree an idempotency
  rule with the sensor/client before adding a unique key.
